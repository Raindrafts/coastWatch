# CoastWatch QA Test Matrix

## Purpose and use

This is the release-traceable test matrix for CoastWatch. It covers the master specification, the locked API contract, and Phases 1–11 of the implementation plan. **Planned** does not mean passed: the QA owner records the command, build/commit, timestamp, and result in the evidence column only after executing the check.

### Status and priority

| Field | Values / rule |
|---|---|
| Status | `Not ready` (dependency absent), `Ready`, `Passed`, `Failed`, `Blocked`, `Not applicable` (with reason). Default every case to `Not ready`. |
| Priority | `P0` blocks a safe/reliable demo or breaches security/privacy; `P1` blocks a required flow; `P2` important quality/usability; `P3` polish or non-critical coverage. |
| Requirement source | `SPEC` refers to the master specification; `API` to `docs/api-contract.md`; `PLAN` to `docs/implementation-plan.md`. |
| Evidence | Record test type, exact command or manual device/browser, date, build/commit, result, and defect ID(s). Do not enter a pass based on code inspection alone. |

## Test environment and shared fixtures

| Item | Required test setup / data |
|---|---|
| Modes | `demo` mode for seeded UI and CSV cases; API integration mode with isolated MongoDB/test database; offline/AI-unavailable mode; production-like config validation mode. |
| Roles | Public reporter, development reporter owner (where supported), analyst, reviewer, administrator, and unauthenticated user. |
| Seed set | Deterministic 15–25 reports and 20–40 social posts, spanning all hazard types/statuses/severities/sources; at least one report without coordinates; at least one high-priority pending report; related and unrelated candidate records. |
| Media | Valid small JPEG/PNG/WEBP within `MAX_UPLOAD_MB`; invalid MIME/extension, oversized image, corrupt file, and no-file fixture. |
| CSV | Valid mixed social data; missing required header; invalid timestamps/coordinates; duplicate `post_id`; formula-leading text; oversize/over-row-limit file; expired, consumed, and forged preview token. |
| Time/network | Fixed UTC clock where possible; mocked AI success, low-confidence, timeout, `503`, map tile/network failure, API `4xx/5xx`, and slow response. |
| Browsers/viewports | Current Chromium, Firefox, Safari/WebKit when available; desktop 1440px; tablet 768px; mobile 320px and 375px; keyboard-only and a screen-reader spot check. |

## QA intake and rolling review protocol

1. A feature owner requests QA only after the owned slice is runnable and supplies the phase/requirements covered, changed paths, exact setup/seed command, test command output, API examples, known limitations, and proposed evidence location.
2. QA first verifies contract and ownership impact, then marks applicable cases `Ready`; missing dependencies remain `Not ready` rather than inferred as passing.
3. QA runs the narrow automated checks and the matching matrix cases, records reproducible evidence, and files defects with severity (`P0`–`P3`), owner/module, environment/build, steps, expected result, actual result, and attachments.
4. The owner fixes defects in their exclusive paths and returns the same handoff. QA re-tests the failed case and any directly affected regression cases; only QA changes the matrix status/evidence.
5. A phase may close only when its P0/P1 cases pass or a named release owner documents an explicit, time-bounded exception. Release readiness requires current evidence for `E2E-01` through `E2E-05`, `SEC-01` through `SEC-03`, and `OPS-02`.

## Initial QA command plan (to execute when workspaces exist)

Use the actual scripts supplied by the Foundation owner; do not substitute successful commands that the repository does not define. Expected command categories are:

```text
npm run lint
npm run typecheck
npm run test
npm run build
npm --workspace apps/api run test:integration
python -m pytest apps/ai
npm --workspace apps/web run test:e2e
```

Actual commands, versions, exit codes, and dates must be entered in the relevant evidence cells at handoff.
